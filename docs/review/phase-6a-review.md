# Phase 6a review packet

Date: 2026-10-21 · Scope: Phase 6 task 3 — the `dqs/publish/` package
(dry-run + live GitHub + fake client), the human approval gate and
`dqs publish preview`. Companion: `docs/phase-notes/phase-6a.md`. The LangGraph
workflow, interrupt/resume approval and `dqs demo` are **not** in this phase.

## What to review first

1. `src/dqs/publish/base.py` — the runtime approval gate, the failed-verification
   refusal, and the idempotent template method (`find` → write → `record`).
2. `src/dqs/publish/github.py` — the deliberately narrow `GitHubClient`
   protocol, branch validation, target-branch-only commits, one-PR logic,
   label step and fail-closed `build_publisher`.
3. `src/dqs/publish/diff.py` — in-memory replay of a `FixPlan` against the real
   files through the Phase-5a allowlist/exact-match helpers; the preview and
   the commit share these bytes.
4. `src/dqs/publish/body.py` + `sanitize.py` — the deterministic body and the
   structural neutralization of model/data text.
5. `src/dqs/publish/dry_run.py` — file layout, `mode=dry_run` row, `file://`
   URL, and the issue preview path.
6. `src/dqs/publish/store.py` — `dq.publications` read/write and the latest
   verified attempt loader.
7. `src/dqs/cli.py` (`publish preview`) and
   `tests/integration/test_publish_cli_e2e.py` — the real persisted-artifact
   command path.
8. `tests/unit/test_publish_github.py` — every safety claim asserted against a
   fake that records calls; no network.

## Weakest points

1. **The idempotency crash window is real.** The `dq.publications` row is
   inserted after the GitHub write. A crash in between can duplicate on retry;
   live mode repairs the common branch/PR case but the table has no constraint
   to make this atomic. Do not describe publishing as exactly-once.
2. **The PyGithub adapter has not been run against a real repository.** Its
   signatures match installed PyGithub 2.10.0, and the publisher is tested
   through the protocol, but only a real token/repo run can catch API drift in
   `get_contents`/`update_file`/label behaviour. The optional live PR in
   PHASES is still unclaimed.
3. **An existing PR is reused without re-checking its diff.** If a crash left
   a PR open and the plan changed before retry, the publisher returns the old
   PR. For 6b, an incident should be immutable after the approval gate (or the
   publisher should verify the stored patch hash) to keep the reviewed diff and
   the open PR identical.
4. **The live path trusts the current working tree.** `build_file_patches`
   reads the checked-out model files. If the local branch differs from
   `GITHUB_BASE_BRANCH`, the preview/commit is based on local content, not the
   remote base. The commit may fail or produce a diff that does not match the
   base; this is acceptable for the single-checkout design but should be
   explicit in the 6b runbook.
5. **Sanitization is deterministic and conservative, not a proof.** The regexes
   cover the required classes, but a determined Unicode/Markdown edge case
   could still render oddly. The important property — no model-authored
   structure, mentions, links or secrets — is tested; do not treat it as a
   general HTML sanitizer.
6. **`dq.publications` has no unique key.** `find` + `record` is not atomic and
   same-timestamp rows make ordering ambiguous. Single-writer use is assumed,
   consistent with `dq.fix_attempts`.

## Risks to carry into Phase 6b

* **Do not let the graph mint an approval.** The interrupt must carry a real
  human action into `ApprovalDecision`; a resumed graph must not construct one
  from state alone. The gate is only meaningful if the workflow cannot
  self-approve.
* **Coordinate status transitions with the publication row.** A resumed run
  that publishes then crashes before updating `dq.incidents` must not publish
  again; the publication lookup is the idempotency anchor, and status should be
  derived/repaired from it.
* **Keep dry-run distinct from live.** A `mode=dry_run` row is a preview, not
  an approved publication. The workflow must not treat it as “published” when
  deciding whether to call GitHub.
* **Check `GITHUB_MODE=live` prerequisites at graph start.** Failing after
  investigation/verification wastes model budget and leaves an incident in a
  confusing state; `build_publisher` already fails closed, so call it early.
* **Wire the ISSUE route.** `create_issue` and the issue preview exist, but the
  workflow still has to build the `IssueDraft`, choose `kind=issue`, and handle
  NONE (no publication) explicitly.
* **Do not edit verification code from a fix.** The publisher trusts
  `VerificationResult.passed`; 6b must keep that object produced only by the
  Phase-5a verifier.
